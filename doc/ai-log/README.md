# AI 使用与过程记录规范

| 项 | 内容 |
|---|---|
| 适用范围 | A～H 全体成员；本仓库全部代码、文档、前端 |
| 依据 | SRS v2.6 补齐课程评分项方案（2026-11-23，A 批准）§7；`doc/context/git-standards.md` v1.2；`doc/context/team-division.md` §3.9 |
| 维护 | A |

> 课程评分要求：后端代码由本人编写，AI 只能辅助；要保留 AI 交互记录和修改痕迹。本目录就是这些过程材料的存放处。**每人的记录由本人自己写**，别人（包括 AI）不能代写个人陈述。

---

## 1. 规则

1. **后端代码由各负责人自己写。** AI 只用于：基础配置（yml、pom 依赖）、通用片段（工具方法、DTO 模板）、接口模板与报错解释。复杂逻辑（状态机、闸门、批量事务、切面、N+1 优化）必须自己写、自己排错。
2. **逐行看懂再提交。** 合并前审核人可随机挑一段让作者讲；讲不清的退回。
3. **保留 AI 交互记录**：每次有意义的 AI 使用写一篇，放 `doc/ai-log/<成员>/YYYY-MM-DD-<主题>.md`（`<成员>` 用 A～H，`<主题>` 用短横线连接的中文或英文短语）。必填字段见 §3。
4. **原始对话导出**（截图或导出文件）放 `doc/ai-log/<成员>/raw/`，文件名与对应 md 同前缀；**单个文件超过 5 MB 的放网盘**，在 md 里留链接和提取码，不要提交进仓库。
5. **保留修改痕迹**：每人用自己的 git 身份提交，不加 `Co-authored-by`；小步提交（一个提交一件事）；PR 里保留讨论和修改轮次。后端 PR 用 **merge commit** 合并，不 squash（git-standards §7，决策 D9）。
6. **PR 描述写「AI 使用说明」**：本 PR 是否用了 AI、用在哪、对应哪篇 ai-log（模板见 git-standards §7.1）。
7. **不得把密码、令牌、Cookie、个人隐私贴进记录**；截图前先打码。

## 2. 每人每周最少过程材料

| 材料 | 数量 |
|---|---|
| ai-log 记录 | ≥ 1 篇（这一周没用 AI 也写一篇，说明「本周未使用 AI」和做了什么） |
| 有意义的提交 | ≥ 3 个（符合 git-standards，不能是「更新文件」这类） |
| PR 审核意见回复 | 对每条意见逐条回复（已改 / 不改及原因） |

## 3. 每篇记录的必填字段

复制 [`_template.md`](./_template.md) 后填写：

| 字段 | 写什么 |
|---|---|
| 日期、成员、关联 PR / Issue | |
| 工具 | 用的 AI 工具与模式（对话、补全、代码审查……） |
| 目的 | 这次想解决什么问题 |
| 提问摘要 | 自己怎么问的（可节选，原文放 `raw/`） |
| AI 给了什么 | 要点；代码只贴关键几行 |
| 采纳了哪些 | 逐条列出 |
| **自己改了哪些、为什么** | 最重要的一栏：AI 哪里错了、不符合本项目约定（如 404 收口、逻辑删除、权限点），自己怎么改的 |
| 怎么验证 | 编译、启动、curl / ApiFox 请求与响应、EXPLAIN、手工越权检查…… |
| 原始记录 | `raw/` 里的文件名，或网盘链接 |

## 4. 目录结构

```
doc/ai-log/
├── README.md          本文件
├── _template.md       单篇记录模板
├── A/
│   ├── 00-前期文档与前端说明.md   A 本人填写（占位）
│   └── raw/
├── B/ … H/            各成员第一次写记录时自己建
```

## 5. 与报告的关系

结题报告第 8 章「AI 优化总结」从这里汇总：各成员 AI 用在哪、人工改了什么、AI 出错的例子与自己如何排查。答辩前每人准备一页「我做了哪些判断」。
