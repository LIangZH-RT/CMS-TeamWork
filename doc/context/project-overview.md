## 应用概述

CMS 是一套面向单个博客网站的内容管理后台，不是博客前台网站。内容编辑使用 CMS 创建和维护 Markdown 文章、摘要、分类、标签、封面图、正文图片和文章音频，并可在正文中引用视频链接；管理员负责审核内容合规性、管理分类和系统权限；审核通过后，系统按照文章的发布时间设置立即发布或定时发布。博客前台通过公开接口读取已发布文章的公开字段，并自行决定如何渲染正文中的视频链接，CMS 不负责博客前台页面的设计和渲染。

## 项目目标

1. 建立独立的博客内容管理后台。
2. 对博客文章进行统一创建、编辑、审核、发布、下架和维护。
3. 通过分类和标签组织文章，并提供按状态、分类、标签、归属编辑和标题的结构化筛选。
4. 为内容编辑和管理员提供互斥且可验证的角色权限。
5. 通过数据归属隔离、状态迁移限制、媒体文件访问控制和操作留痕，防止未授权访问和未审核内容公开。
6. 通过公开内容接口向博客前台提供已发布文章的数据。

## 核心用户流程：从创建到结束

1. **准备账号并登录 CMS。** 当前测试环境中，内容编辑（创作者）通过注册入口直接注册并立即启用；管理员账号不开放注册，只在数据库初始化时创建一个且仅一个账号。本期不提供密码找回、邮件验证或自助重置；测试环境账号恢复通过数据库初始化或维护脚本完成。账号准备完成后，内容编辑或管理员使用密码登录，系统建立服务端会话，使用 httpOnly Cookie，并启用 CSRF 防护。未认证请求不能访问后台接口。
2. **创建文章草稿。** 内容编辑创建文章，填写标题、Markdown 正文、可选摘要、必选分类、可选标签和可选预定发布时间，并按需上传封面图、正文图片和文章音频。正文可以引用视频链接，CMS 只保存链接本身、不限制来源域名，也不保存任何嵌入代码或视频文件；何时以及如何渲染由博客前台决定。文章创建后归属于创建它的编辑。
3. **保存和修改草稿。** 内容编辑只能读取和修改自己创建的文章。处于草稿、驳回或已下架状态的文章可以修改；处于待审核、待发布或已发布状态的文章不能直接修改。
4. **处理未提交草稿。** 从未提交过且没有任何操作留痕的草稿可以由归属编辑删除。删除必须二次确认，属于物理删除且不可撤销。管理员不能删除该草稿。
5. **提交审核。** 归属编辑将草稿、驳回文章或已下架文章提交审核。系统把状态改为「待审核」，写入提交时间，并生成操作留痕。编辑不能直接设置状态或直接发布文章。
6. **管理员审核。** 管理员在审核队列中查看待审核文章，但不能修改文章正文或其他内容字段。管理员有两种处理结果：
   - 驳回：必须填写非空、非纯空格的驳回意见，状态变为「驳回」，意见进入留痕并对归属编辑可见；
   - 通过：系统根据预定发布时间决定后续状态，不存在独立的人工“发布”按钮。
7. **审核通过后的发布分支。** 未设置预定时间，或预定时间已经到达或超过当前时间时，系统立即将文章置为「已发布」并写入实际发布时间；预定时间在未来时，文章进入「待发布」。
8. **待发布期间纠错。** 在预定时间到达前，归属编辑可以把预定时间改为未来的其他时间，文章保持「待发布」且原审核结论继续有效；也可以撤回文章，文章回到「草稿」、预定时间被清空、原审核结论作废，并且再次上线必须重新提交审核。改期和撤回都生成留痕。
9. **系统定时发布。** 系统定时查找已审核通过且预定时间已到达的「待发布」文章，将其置为「已发布」，写入系统实际执行时间，并生成系统操作留痕。任务重复执行不能覆盖已有实际发布时间，也不能重复发布同一篇文章。
10. **已发布内容公开。** 博客前台只能通过公开接口读取「已发布」文章的公开字段，包括标题、摘要、Markdown 正文、分类、标签、封面图地址、文章音频地址和实际发布时间。草稿、待审核、驳回、待发布和已下架文章不能通过公开接口读取。
11. **下架与重新上线。** 管理员可以将已发布文章下架，但必须填写下架原因。下架后文章、封面图、正文图片和文章音频立即停止匿名访问；归属编辑可以修改已下架文章并重新提交审核，但管理员不能直接恢复上线。
12. **查看操作留痕。** 归属编辑可以查看自己文章的全部留痕，管理员可以查看全部文章的留痕。留痕只能新增，不能修改或删除。

## 功能部分

### 认证与会话

提供账号密码登录、登出、服务端会话、httpOnly Cookie、CSRF 防护和未认证请求拦截。测试环境允许内容编辑账号直接注册并立即启用；管理员账号不开放注册，只在数据库初始化时创建唯一账号。本期不提供密码找回、邮件验证、重置令牌或自助改密。系统角色分为内容编辑和管理员，一个账号只能拥有一个角色。

### 文章与草稿管理

提供文章创建、保存、编辑、详情查看、列表查看和受限删除。文章正文保存为 Markdown 原文；摘要可为空，CMS 不自动从正文截取摘要。每篇文章有唯一归属编辑，编辑只能访问自己的文章，管理员可以查看全部文章但不能替编辑修改文章内容。

### 提交、审核与下架

提供草稿提交审核、审核队列、审核通过、驳回和已发布文章下架。驳回意见和下架原因均由服务端强制要求，空字符串和纯空格均视为未填写。

### 状态与自动发布

实现 6 个文章状态：草稿、待审核、驳回、待发布、已发布、已下架。文章只能沿 SRS 定义的 11 条状态迁移路径变化；不存在直接修改状态字段的接口，也不存在独立人工发布接口。系统负责立即发布和到期自动发布。

### 分类、标签与结构化筛选

分类是单选、封闭集合，由管理员维护；标签是多选、开放集合，可以由编辑随文创建，不建立层级关系。文章列表和公开文章接口支持按状态、分类、标签、归属编辑筛选以及标题模糊匹配；多标签筛选使用交集语义，不提供正文全文检索。

### 媒体资源

支持上传一张封面图、多张正文图片和一篇文章音频。所有上传文件都必须通过类型白名单和大小上限校验，文件名由系统生成，不使用用户提供的文件名拼接路径。封面图、正文图片和文章音频的访问权限都与文章状态绑定：只有已发布文章的媒体文件允许匿名访问，其他状态的媒体文件必须经过后台权限校验。

正文中的视频**只保存链接**：CMS 不限制来源域名，但绝不保存 HTML、脚本、iframe 或任何播放器嵌入代码——正文里存的始终是一个 URL，渲染由博客前台自行决定。CMS 不上传、不下载、不代理、不转码视频文件。

### 操作留痕

对提交审核、审核通过、驳回、下架、撤回和改期记录文章操作历史，至少保存文章、操作类型、操作人、操作时间和原因/意见。留痕只增不改不删，并且查询同样受文章归属隔离约束。

### 用户与权限管理

当前版本包含内容编辑账号直接注册、管理员账号数据库初始化、登录、角色判定和权限边界。本期不提供密码找回、邮件验证、密码重置或自助改密；账号恢复通过数据库初始化或维护脚本完成。账号角色修改、账号停用以及文章归属改派仍属于后续版本事项，不能被当作当前版本的完整验收功能。

### 博客前台公开接口

提供已发布文章列表和详情接口，支持分页、分类筛选和多标签交集筛选。接口不得返回非已发布文章、未公开正文或受保护的封面资源，也不得提供可通过状态参数绕过公开限制的入口。

## 成功标准：什么情况算完成

项目只有同时满足功能、权限、安全、数据和验收条件时才算完成：

1. SRS 中定义的 37 条功能需求均有实现或明确标记为后续版本；当前版本不能把后续版本的用户管理功能伪装成已完成。
2. 53 条业务规则、6 个文章状态和 11 条状态迁移路径在代码、数据库约束、接口行为和自动化测试中保持一致。
3. 已发布文章的唯一业务入口是管理员审核通过；编辑不能发布，管理员不能手动发布，已下架文章不能直接恢复上线。
4. 编辑 A 对编辑 B 的文章详情、编辑、删除、提交、筛选、计数、留痕和封面访问全部不可用，并统一返回与资源不存在一致的 404 响应；管理员可以访问全部文章但不能直接修改文章内容。
5. 草稿、待审核、驳回、待发布和已下架文章的正文、正文内上传图片、封面图、文章音频和正文中的视频链接不能被匿名访问；文章下架后，全部媒体文件必须立即停止匿名访问。
6. 驳回意见和下架原因由服务端强制校验；缺失、空字符串或纯空格都必须导致操作失败且文章状态不变。
7. 所有改变状态的操作只能通过既定迁移接口完成；直接提交 `status` 字段、非法迁移、重复提交和不符合状态条件的操作都不能改变数据。
8. 定时发布任务只处理已审核通过且到期的待发布文章，支持重复触发而不重复发布、不覆盖实际发布时间，并且单篇失败不阻塞其他文章。
9. 操作留痕对规定的状态迁移和改期完整记录，任何用户和管理员都不能修改或删除留痕。
10. 公开文章接口只返回已发布文章及其公开字段，多标签筛选严格采用交集语义，不能通过筛选参数或计数结果推断未授权文章。
11. 追溯校验脚本通过，`doc/context/project-overview.md` 的业务规则与 SRS 内置的权限矩阵、用例、状态迁移、留痕类别、需求编号和关键验收数据保持一致。

## 4. 角色

本期 CMS 后台的账号体系为两类，共 N+1 个账号 [已定]：

| 角色 | 人数 | 职责 |
|---|---|---|
| 内容编辑 | N | 内容生产与维护，**没有最终发布权限** |
| 管理员 | 1 | 内容合规性审核 + CMS 整体管理 |

角色设计的基本思想是**内容生产与内容管理/审核分离**。内容编辑是"负责生产和维护博客内容、但没有最终发布权限的工作人员"。

### 4.1 角色是互斥的

- **BR-ROLE-001** 一个账号**只能有一个**角色，不支持兼任：账号或是内容编辑、或是管理员，不存在"既是编辑又是管理员"的账号。[已定]
- **BR-ROLE-002** 管理员不下场写稿。管理员若要写文章，需另开一个内容编辑账号。
- **BR-ROLE-003** **审核独立性由角色模型结构性保证，不依赖运行时校验**：因为管理员不写稿，任何文章的作者必然是内容编辑，而审核者必然是他人的管理员账号——`author ≠ reviewer` 是模型自带的结论，系统不需要额外写"禁止自审"的校验逻辑。

> 这条的性质值得注意：它不是"多加一条规则"，而是**用角色结构消掉了一类问题**。若允许兼任，就必须在运行时校验"审核人不能是作者"，而那个校验一旦漏写就是漏洞；互斥角色把这个漏洞从根上取消了。

**访客与博客读者不进入本系统账号体系**——他们属于博客前台，CMS 只对已发布内容提供数据。

### 4.2 账号创建与密码规则

- 当前测试环境中，内容编辑账号（创作者账号）可以通过注册入口直接注册，注册成功后立即启用，不需要管理员审核。
- 管理员账号不开放注册；每个测试数据库在初始化时创建一个且仅一个管理员账号。
- 本期不提供密码找回、邮件验证、密码重置令牌或自助改密接口。测试环境账号恢复通过数据库初始化或维护脚本完成。

## 5. 内容生命周期

采用"编辑—审核—发布"流程 [已定]：

```
                    ┌──────────────────────────────────────────────┐
                    │                                              │
                    ▼                                              │
  ┌──────┐  编辑提交   ┌────────┐  审核不通过   ┌──────┐  编辑修改后   │
  │ 草稿 │ ─────────→ │ 待审核 │ ───────────→ │ 驳回 │  重新提交     │
  └──────┘            └────────┘              └──────┘ ────────────┘
     ▲                     │
     │ 编辑撤回             │ 审核通过
     │                     ├────────────────────────────┐
     │                     │ 无预定时间 / 预定时间已到    │ 有未来的预定时间
     │                     ▼                            ▼
     │                ┌────────┐                  ┌────────┐
     │                │ 已发布 │ ←─── 系统定时 ─── │ 待发布 │
     │                └────────┘                  └────────┘
     │                     │                          │
     │                     │ 管理员下架                └── 编辑可改期（留在本状态）
     │                     ▼
     │                ┌────────┐
     └── 编辑修改后 ── │ 已下架 │
        重新提交审核    └────────┘
```

十一条状态迁移路径，按触发者归类（第 11 条是终结操作，不产生新状态）：

| # | 触发者 | 迁移 |
|---|---|---|
| 1 | 归属编辑 | 草稿 → 待审核（提交） |
| 2 | 归属编辑 | 驳回 → 待审核（修改后重新提交） |
| 3 | 归属编辑 | 待发布 → 待发布（改期，内容不变，审核结论继续有效） |
| 4 | 归属编辑 | 待发布 → 草稿（撤回，审核结论作废，需重新过审） |
| 5 | 归属编辑 | 已下架 → 待审核（修改后重新提交） |
| 6 | 管理员 | 待审核 → 驳回（必须填驳回意见） |
| 7 | 管理员 | 待审核 → 已发布（未设预定时间，或预定时间已到） |
| 8 | 管理员 | 待审核 → 待发布（设有未来的预定时间） |
| 9 | 管理员 | 已发布 → 已下架 |
| 10 | 系统 | 待发布 → 已发布（到达 `scheduled_publish_time` 时自动触发） |
| 11 | 归属编辑 | 草稿 → **删除**（记录消失；仅限从未提交过的草稿，见 6.6） |

**不存在的路径同样重要**（这些是必须被测试证明无法走通的）：编辑 → 已发布、管理员 → 手动发布、已下架 → 已发布（直连）、非草稿 → 删除、编辑 → 读写他人文章。

**全流程不变量：已发布的唯一入口是「审核通过」。** 除审核通过外，不存在任何使文章进入已发布的路径——编辑不能自行发布，管理员不能手动发布（BR-PUB-001），下架文章也不能直接恢复上线。这条不变量是权限模型可证明的关键：只要它成立，"任何未过审内容都不会对外展示"就能被穷举验证。

### 5.1 文章状态

系统共维护 **6 个**文章状态：

| 状态 | 含义 |
|---|---|
| 草稿 | 编辑正在创建或修改，尚未提交 |
| 待审核 | 已提交，等待管理员审核 |
| 驳回 | 管理员审核不通过，等待编辑按驳回意见修改后重新提交 |
| 待发布 | 已审核通过，等待预定发布时间到达；归属编辑可在此期间改期或撤回 |
| 已发布 | 已经对博客前台公开 |
| 已下架 | 曾经发布，被管理员下架，当前不再公开 |

「驳回」是**独立状态**，不是「草稿」的同义词 [已定]。理由是"状态可见性"：编辑必须能从文章列表中一眼分辨"这篇还没写完"和"这篇被打回了"，否则会反复提交同一篇稿。驳回意见（驳回人、时间、原因）挂在该状态上，进入列表与详情页时直接可见。

「已下架」是**可修复的状态，不是终态** [已定]。归属编辑可以修改已下架文章并重新提交审核，审核通过后回到「已发布」。下架文章**不能**由管理员直接恢复上线——恢复必须重新过审，以维持第 5 节的不变量。

「待发布」是**可纠错的窗口，不是锁定态** [已定]。归属编辑在预定时间到达前可改期（审核结论继续有效）或撤回（审核结论作废、回到草稿、需重新过审）。「已发布」之后则不能再撤回，只能走下架路径。

> 来源对话此处自相矛盾——§6.2 的状态表把「审核驳回」列为独立状态，§6.7.5 的最终状态表却把它画成回到「草稿」。本基线采用前者，即独立状态。

## 6. 业务规则

来源对话中存在**两套编号重叠、内容冲突的 BR 规则**（§6.6 的 BR-001~BR-009 与 §8 的 BR-001~BR-007 各说一套）。以下重新统一编号，内容不变。

### 6.1 提交与审核

- **BR-001** 只有处于「草稿」「驳回」或「已下架」状态的文章可以提交审核。
- **BR-002** 处于「待审核」状态的文章，内容编辑不能直接修改；需先由管理员退回。
- **BR-003** 管理员确认文章符合发布要求后，状态由「待审核」进入发布流程。
- **BR-004** 管理员认为需要修改时驳回，状态由「待审核」变为「驳回」，**必须填写驳回意见**，该意见作为编辑修改的依据。
- **BR-005** 处于「驳回」状态的文章，编辑修改完成后可重新提交审核，状态回到「待审核」。
- **BR-006** 内容编辑不能直接将文章置为「已发布」，也不能通过改状态绕过审核流程。
- **BR-007** 管理员不能直接修改文章内容（不改标题、不改正文、不替编辑润色、不决定内容方向）；管理员的审核依据只有"是否符合网站内容合规规范"。
- **BR-008** 管理员可以将已发布的文章下架，下架后不再对博客前台公开。下架时**必须填写下架原因**，该原因记入审核历史并对归属编辑可见（与驳回意见同构）。
- **BR-009** 系统应保存文章的审核历史用于追踪。
- **BR-010** **已发布的唯一入口是审核通过**。不存在其他使文章进入「已发布」的路径：编辑不能自行发布、管理员不能手动发布、下架文章不能被直接恢复上线。
- **BR-011** 「已下架」不是终态：归属编辑修改后可重新提交审核，走 BR-001→BR-003 的正常路径回到「已发布」。

### 6.2 自动发布

- **BR-PUB-001** 管理员审核通过后**由系统自动触发发布**，管理员不需要、也不应该再次点击"发布"。
- **BR-PUB-002** 作者可以选择是否设置预定发布时间。
- **BR-PUB-003** 未设置预定时间的文章，审核通过后立即发布，`published_at` = 审核通过时间。
- **BR-PUB-004** 设置了未来预定时间的文章，审核通过后进入「待发布」，等待到 `scheduled_publish_time` 自动发布。
- **BR-PUB-005** 审核通过时若预定时间**已经到达或超过**，立即发布，**不顺延**。（理由：审核通过 = 内容具备发布资格，系统不应替作者改写发布计划。）
- **BR-PUB-006** `published_at` 由系统在真正发布时写入，内容编辑和管理员都不能手动伪造。
- **BR-PUB-007** 只有经过管理员审核通过的文章，系统才允许进入自动发布流程。
- **BR-PUB-008** 「待发布」**不是锁定态**，而是一个可纠错的窗口：归属编辑在预定时间到达之前，可以修改 `scheduled_publish_time` 改期，内容未变，原审核结论继续有效；新的预定时间必须晚于当前时间，传入当前时间或过去时间的值必须被拒绝，也可以撤回。
- **BR-PUB-009** 撤回后状态回到「草稿」，审核结论同时作废，要再次上线必须重新提交审核并重新过审。撤回不产生驳回记录，但应记入操作日志。
- **BR-PUB-010** 文章一旦进入「已发布」，就**不能再撤回**，只能走下架路径（BR-008）。

> 改期只修改 `scheduled_publish_time`，不改变文章内容，因此原审核结论继续有效。为了避免把已到期文章重新放入待发布窗口，新时间必须晚于当前时间；当前时间或过去时间的值必须拒绝。

### 6.3 发布时间字段

系统维护两个职责不同、不允许混用的时间字段 [已定]：

| 字段 | 含义 | 设置方 |
|---|---|---|
| `scheduled_publish_time` | 作者预定的发布时间，可为空 | 内容编辑设置 |
| `published_at` | 文章实际对外发布的时间 | 系统写入 |

### 6.4 内容筛选

- **BR-SEARCH-001** 文章的查找能力为**结构化筛选**：按状态、分类、标签、归属编辑筛选，并对标题做模糊匹配。**不提供正文检索**（不建全文索引、不引入检索引擎）。[已定]
- **BR-SEARCH-002** 筛选与关键字不得构成绕过列表的例外查询路径——它必须走与列表同一套归属过滤。
- **BR-SEARCH-003** 筛选结果同样受 BR-ISO-001 约束：编辑只能筛出自己的文章，管理员可筛全部；分页与计数也必须基于过滤后的结果集，不能先全量计数再过滤（那会通过总数泄露他人文章的存在）。
- **BR-SEARCH-004** 一篇文章可以带**多个标签**，标签是多对多关系（需要 `article_tag` 中间表）。
- **BR-SEARCH-005** 选中多个标签时，筛选语义为**交集（AND）**——只返回同时具备全部选中标签的文章。这与 LeetCode 的标签筛选行为一致：勾选"Java"和"教程"两个标签，得到的是"既是 Java 又是教程"的题目，而不是其中之一。
- **BR-SEARCH-006** 标签是**扁平集合**，不建层级、不做父子关系（区别于分类）。

> 实现提醒（属 `architecture.md`）：N:M 之上的交集筛选不能用简单的 `IN` 搞定——`tag_id IN (1,2)` 是并集语义，会多返回只命中一个标签的文章。要按"分组计数"或"每个标签各连一次"来实现，且这套计数必须与 BR-SEARCH-003 的过滤后分页一起处理，否则分页总数会重新泄露信息。

### 6.5 媒体资源

封面图、正文图片与文章音频纳入本期范围 [已定]，由此带出文件上传、存储和媒体文件访问控制；正文视频只保存链接。

- **BR-MEDIA-001** 文章可以设置一张封面图；Markdown 正文可以插入通过 CMS 上传的图片。封面图和正文图片均不采用外部图片链接。
- **BR-MEDIA-002** 上传封面图、正文图片或文章音频时，文件类型必须在对应的类型白名单内且不超过大小上限；存储文件名由系统生成，不采用用户提供的文件名与扩展名。**图片白名单为 `jpg`／`jpeg`／`png`／`gif`／`webp`、单文件上限 5 MB**，封面图与正文图片共用同一份白名单；音频白名单见 BR-MEDIA-005。本期不上传视频文件或任意其他文件。[已定 2026-09-29]
- **BR-MEDIA-003** 封面图、正文图片与文章音频的访问控制与文章状态绑定：草稿、待审核、驳回、待发布、已下架五种状态下，这些文件不能被匿名访问，只有已发布文章的文件才可公开。正文中的视频链接同样不能通过未发布文章接口泄露。
- **BR-MEDIA-004** 替换封面图、正文图片或文章音频、删除文章后，相关旧文件需要清理。
- **BR-MEDIA-005** 文章可以设置**一个可选音频文件**，与封面图同构：每篇最多一个，必须通过 CMS 上传，不采用外部音频链接。音频的类型白名单为 `mp3`／`m4a`／`wav`／`ogg`，单文件大小上限 20 MB [已定 2026-09-29]。
- **BR-MEDIA-006** 正文中的视频**只保存链接**：CMS 存的是一个 URL，**不限制来源域名**，但**不接受 HTML、脚本、iframe 或任何播放器嵌入代码**；链接协议必须为 `https` [已定 2026-09-29]。校验只发生在链接层面，CMS 不判断链接目标的实际内容——内容是否对外公开由管理员审核决定。
- **BR-MEDIA-007** CMS 不下载、不代理、不转码视频文件，因此不产生 CMS 侧的视频文件清理任务；前台是否内嵌播放器、如何内嵌，属于博客前台的范围。

> **为什么"支持所有来源"落在"只存链接"这一层（2026-09-29 拍板）。** 如果允许编辑粘贴平台给出的嵌入代码，CMS 就得在正文里存原始 HTML，前台 Markdown 渲染器必须打开 raw HTML 直通才能把它渲染出来——那是最经典的 XSS 现场。而且这条路**挡不住**：审核看到的是一段代码，而代码的行为和它指向的页面都可以在事后被第三方改掉。改为只存链接，等于把"任意 URL 进不来"这条约束换成"任意 URL 可以进来，但它只能是一个 URL"。代价是域名白名单这道可证明的防线消失，把关集中到人工审核上——这是客户明确选择并已知代价的取舍。

> **为什么音频与封面图同构，而不是放正文（2026-09-29 拍板）。** 同构意味着权限判定、状态绑定、替换与删除时的清理规则可以整条复用，几乎不新增规则；代价是一篇文章只能有一个音频。若改为正文内可插入多个音频，`media_file` 必须能区分用途，且删除文章时要扫描正文找出全部引用再逐个清理。

> **为什么图片白名单不含 `svg`。** SVG 是 XML，可以内嵌 `<script>`。用 `<img>` 加载它不会执行脚本，但不少 Markdown 渲染器与图片预览组件是**内联**渲染的——一旦内联，它就是一个存储在 CMS 里的 XSS 载荷。要允许 SVG 就必须额外规定"前台一律以 `img` 方式加载"，而这条约束落在博客前台、不在本期交付范围内，无法在验收时测到。因此白名单里不放 SVG；需要矢量图时走 `png`。

> BR-MEDIA-003 值得单独强调：整份基线里其他越权风险都落在数据行上，而这条落在**静态资源**上。文章列表做了归属过滤，媒体文件却没有——这类漏洞在演示时不会被界面暴露，只能靠测试兜。

### 6.6 文章删除

- **BR-DEL-001** 只有**从未提交过的「草稿」**可以被删除，即状态为「草稿」**且没有任何留痕**的文章。其他五种状态、以及"提交过又被撤回"的草稿，一律不可删除。要把已发布文章从线上撤下，走下架（BR-008），不走删除。
- **BR-DEL-002** 删除是**物理删除**，不是软删除：记录从 `article` 表移除，不留删除标记。按 BR-DEL-001 的定义，可删除的文章必然没有任何留痕，因此不会产生指向不存在文章的孤儿留痕，也不与 BR-AUDIT-001（留痕只增不删）冲突。
- **BR-DEL-003** 删除权限归**归属编辑本人**（受 BR-ISO-001 约束）。管理员**不能**删除他人草稿——管理员要处理内容用下架，保持"管理员不改内容"的边界（BR-007）。
- **BR-DEL-004** 删除文章时，其封面图文件一并清理（BR-MEDIA-004 的落地）。
- **BR-DEL-005** 删除不可撤销，界面上必须二次确认。

> 这条规则把"删除"限定在最小的安全范围内：它是给作者清理**从未提交过的草稿**用的，不是一条绕过审核与下架的旁路。若允许删除已提交的文章，就等于给"内容消失"开了第二个入口，与 BR-010 的不变量精神相冲。

> **【数据库设计阶段发现的冲突，2026-09-28 已修正】** 本节最初写的是"草稿可以删除"，理由是"草稿从未提交、没有留痕"。但 BR-PUB-009 规定撤回后文章回到「草稿」并产生留痕——**撤回产生的草稿是有留痕的**。"草稿"这个状态里实际混了两类东西：从未提交过的，与提交过又撤回的；原规则把它们当成一类，理由是错的。已把可删除条件精化为"草稿**且无任何留痕**"。这样 `audit_log.article_id` 的外键设 `ON DELETE RESTRICT` 就能在数据库层直接落实该规则，无需应用层再查一次。

## 7. 审核记录

系统保存文章的完整操作留痕，至少包含：文章 ID、操作类型、操作人、操作时间、原因/意见 [已定]。

### 7.1 需要留痕的操作

留痕**共 7 类**。操作人一栏有两种主体：人类账号（归属编辑 / 管理员）与**系统**。最后一列把每类留痕钉回 §5 的迁移路径，两者可以逐条对照。

| 操作类型 | 操作人 | 原因/意见 | 对应迁移路径 |
|---|---|---|---|
| 提交审核 | 归属编辑 | 否 | #1、#2、#5 |
| 审核通过 | 管理员 | 否 | #7、#8 |
| 驳回 | 管理员 | **必填**（驳回意见） | #6 |
| 下架 | 管理员 | **必填**（下架原因） | #9 |
| 撤回 | 归属编辑 | 否 | #4 |
| 改期 | 归属编辑 | 否 | #3 |
| 到期自动发布 | **系统** | 否 | #10 |

11 条迁移路径各自落在这张表的某一类里，只有一条例外：**#11（草稿 → 删除）不留痕**，因为它按 BR-DEL-001 只作用于从未提交过、没有任何留痕的文章，记录本身也随之消失（BR-DEL-002）。

> 「改期」是否留痕是我补的——它改变了文章对外可见的时间点，属于需要追溯的操作。若客户认为不必留痕，我把它划掉。

> **为什么操作人必须是两种主体（2026-09-29 拍板）。** 迁移路径 #10 是 11 条里唯一「没有人工操作人、到点自己发生」的一条，而核心流程 §9 与 X-AUDIT-01 都要求它生成留痕。若操作人只有人类角色，这条留痕不是"可以省略"，而是**根本写不进去**——表里没有一个能指向"系统"的取值。因此把操作人拆成 `USER` / `SYSTEM` 两种主体（BR-AUDIT-004）：人类主体必须指向一个账号，系统主体必须不指向任何账号。
>
> 没有采用「把系统建成一个不可登录的账号」。它能让外键保持非空，但代价是账号体系从两类变三类、`user` 表混入一条非人记录，于是「每库仅一个管理员」这类初始化断言、角色闸、归属编辑枚举都要跟着重写——用一处表结构的表达力，换一串语义污染。
>
> 也没有采用「谁触发 / 谁执行」两对列。到期自动发布确实存在"是谁把它送到待发布的"这个问题，但那个事实**已经**在留痕表里：文章进「待发布」只可能来自路径 #8（审核通过）或路径 #3（改期），两条都各自有留痕。再存一列就是给已有事实立第二份副本，而副本会不一致。


### 7.2 约束

- **BR-AUDIT-001** 留痕记录**只增不改不删**，不提供修改与删除接口（包括管理员）。
- **BR-AUDIT-002** 归属编辑可以查看**自己文章**的全部留痕；管理员可以查看全部文章的留痕。此条同样受 BR-ISO-001 约束，不能成为绕过隔离的通道。
- **BR-AUDIT-003** 驳回意见与下架原因是**强制字段**：对应操作在无原因时不允许提交。空字符串、纯空格视为未填写。
- **BR-AUDIT-004** 留痕的操作人是**双主体**的：主体类型为 `USER` 时必须指向一个账号，主体类型为 `SYSTEM` 时必须**不**指向任何账号，两者不可互换、也不能只存其一。**系统主体只用于没有人工触发者的迁移**，当前仅「到期自动发布」一类 [已定 2026-09-29]。


### 7.3 样例

样例刻意做成三篇文章，把 7 类留痕全部覆盖到一遍——包括那条没有账号的「系统」。

```
文章：《Spring Boot 入门教程》   （未设预定时间 → 审核通过即发布）

2026-09-28 10:00  张三（编辑）    提交审核
2026-09-28 10:30  李四（管理员）  驳回      意见：正文缺少实际案例
2026-09-28 14:00  张三（编辑）    提交审核
2026-09-28 15:20  李四（管理员）  审核通过
2026-10-02 09:00  李四（管理员）  下架      原因：技术结论已过期，需更新

文章：《Vue 3 组合式 API 笔记》   （设有未来预定时间 → 进「待发布」，到点自动上线）

2026-09-28 16:00  张三（编辑）    提交审核
2026-09-28 16:20  李四（管理员）  审核通过
2026-09-29 11:00  张三（编辑）    改期      新时间：2026-10-04 09:00
2026-10-04 09:00  系统            到期自动发布

文章：《草稿：Docker 入门》       （待发布期间撤回，审核结论作废）

2026-09-28 17:00  张三（编辑）    提交审核
2026-09-28 17:20  李四（管理员）  审核通过
2026-09-29 09:00  张三（编辑）    撤回
```

注意第二篇里「到期自动发布」那一行：它没有账号，也没有人点过任何按钮，时间到了自己发生。这正是 BR-AUDIT-004 要表达的东西——留痕的操作人不总是人。


## 8. 权限矩阵

依据来源对话的权限表整理，并修正其与自动发布规则冲突之处 [已定，除标注外]：

| 功能 | 内容编辑 | 管理员 |
|---|:---:|:---:|
| 创建文章 | ✓ | — |
| 编辑文章 | ✓ | — |
| 保存草稿 | ✓ | — |
| 设置分类 / 标签 / 预定发布时间 | ✓ | — |
| 提交审核 | ✓ | — |
| 读写**他人**的文章 | — | ✓ |
| 查看审核结果与驳回意见 | ✓ | ✓ |
| 合规性审核 / 审核通过 / 驳回 | — | ✓ |
| 下架已发布文章 | — | ✓ |
| 用户管理（当前版本无后台建号、改角色接口） | — | — |
| 分类 / 标签管理 | 可配置 | ✓ |
| 发布文章 | — | — |

> **发布一行是为空的**。来源对话的权限表给管理员标了「发布文章 ✓」，但同一会话随后确定了"审核通过后系统自动发布、管理员不再点击发布"。保留该权限点会与 BR-PUB-001 直接冲突，故此处清空，需你确认。

### 8.1 数据归属与隔离

- **BR-ISO-001** 每篇文章有唯一的归属编辑（创建人）。内容编辑只能读写**自己创建**的文章，管理员可读写全部文章。[已定]
- **BR-ISO-002** 隔离对所有状态一视同仁：草稿、待审核、驳回、待发布、已发布、已下架，编辑都只能看到自己的。不因"已发布"而对其他编辑开放。
- **BR-ISO-003** 隔离在**数据层**强制执行，不是在界面上隐藏入口。所有涉及文章的查询与写接口都必须附加归属条件，漏一处即构成越权漏洞。
- **BR-ISO-004** 隔离只针对 CMS 后台管理接口。博客前台是公开消费方，通过独立接口读取**已发布**文章的公开字段，不受本条影响——但该接口不得返回待审核、待发布、已下架内容。

> 这一条是整套需求里唯一具有技术分量的部分：**同角色之间的越权场景**（两个编辑）无法靠隐藏按钮蒙混过关，只能靠数据层归属过滤实现。它同时是"任意角色在任何接口上都不能读写他人数据"这条验收标准的成立前提。

> 归属字段的**实现方式**（MyBatis-Plus 行级拦截器自动追加，还是每个查询手写条件；管理员绕过拦截器的路径如何避免成为后门）属于 `architecture.md`，此处只定规则不定手段。

## 9. 待澄清项汇总

实现前必须逐条拍板，否则会在数据库与接口层返工。

### 9.1 已搁置（账号域后续处理）

1. 归属编辑的账号被停用或离职后，其名下文章成为“孤儿”——管理员不能改内容（BR-007），编辑又不能代管（BR-ISO-001），文章会卡死。是否需要“改派归属编辑”的能力？

账号注册方式和当前测试环境的密码策略已经确定，不再属于待澄清项。账号停用、角色修改和文章改派仍需在后续版本确定；它们不阻塞文章域实现。

### 9.2 待关闭

**暂无待关闭项（2026-09-29 清空）。** 同日先补上了图片类型白名单与单文件大小上限（见 BR-MEDIA-002），这是本次核对音频取值时连带发现的一处缺口：BR-MEDIA-002 原写"必须在**对应的**类型白名单内"，而 SRS §7.2 的封面图一行写"见 6.4 媒体资源规则"——规则说要查白名单、字段清单说去看规则，**两侧互相指认，那张表从未存在过**。

同日还有第二处同类缺口，在架构设计阶段核对留痕表时发现并当场关闭：**到期自动发布没有对应的留痕类别**（见 7.1 与 BR-AUDIT-004）。核心流程 §9 与 X-AUDIT-01 都要求这条迁移生成留痕，而 §7.1 的操作人一栏只有人类角色——留痕表里没有任何取值能表示"系统"，这条留痕根本写不进去。两处缺口的形状是一样的：**一条规则指着一份从未存在、或早已漏项的清单**；而且清单在两份文档里各抄了一份、彼此吻合，看上去反而更自洽。

### 9.3 已关闭

- 驳回后的归属状态 → 独立「驳回」状态（见 5.1 与 BR-004、BR-005）
- 编辑之间是否数据隔离 → 隔离到文章，仅限本人创建（见 8.1）
- 管理员能否手动发布 → 不能，发布由系统自动触发（见 BR-PUB-001）
- 已下架文章能否重新上线 → 能，但必须重新过审，不能直接恢复（见 5.1、BR-010、BR-011）
- 待发布文章能否改期或撤回 → 都能；改期不重审，撤回回到草稿并需重新过审（见 BR-PUB-008~010）
- 内容搜索的口径 → 只做结构化筛选，不提供正文检索（见 6.4）
- 管理员能否兼任编辑 → 不能，角色互斥（见 4.1 与 BR-ROLE-001~003）
- 下架时是否必须填下架原因 → 必须填，与驳回意见同构（见 BR-008、BR-AUDIT-003）
- 分类与标签的关系 → 分类单选、封闭集合；标签多选、开放集合（见 10.1 与 BR-TAX-001~003）
- 封面图与正文图片 → 纳入本期，访问控制须与文章状态绑定（见 6.5 与 BR-MEDIA-001~004）
- 视频链接的来源范围与保存形态 → **不限来源域名，但只保存链接**，不接受 HTML／脚本／iframe／播放器嵌入代码（见 6.5 与 BR-MEDIA-006~007）
- 音频媒体 → 纳入本期，**上传音频文件**，作为文章的一个可选字段与封面图同构（见 6.5 与 BR-MEDIA-005）
- 音频类型白名单与大小上限、视频链接协议 → `mp3`／`m4a`／`wav`／`ogg`、20 MB、`https`（见 6.5 与 BR-MEDIA-005~006）
- 图片类型白名单与大小上限 → `jpg`／`jpeg`／`png`／`gif`／`webp`、单文件 5 MB，封面图与正文图片共用；**不含 `svg`**（见 6.5 与 BR-MEDIA-002）
- 文章删除的语义 → 仅「草稿」可硬删除，其他状态不可删（见 6.6 与 BR-DEL-001~005）
- 摘要的来源 → 选填，作者不写即为空，**CMS 不做自动截取**（见 10.2）
- 到期自动发布是否需要留痕 → **需要**；新增第 7 类留痕「到期自动发布」（见 7.1）
- 留痕的操作人能否表达"系统" → **能**；操作人采用 `USER` / `SYSTEM` 双主体模型，人类主体必指向账号、系统主体必不指向（见 7.1、BR-AUDIT-004）

## 10. 文章内容模型（字段清单）

来源对话正停在这一步。以下字段清单直接决定 `article` 表与文章管理页面。标注 **[建议]** 的是我给出的默认值，客户未明确表态前可推翻。

### 10.1 分类与标签的关系

- **BR-TAX-001** 分类**单选**：一篇文章只属于一个分类，`article.category_id` 外键。
- **BR-TAX-002** 标签**多选**：一篇可有多个标签，N:M 关系，需要 `article_tag` 中间表。
- **BR-TAX-003** 两者职责不同：**分类是封闭集合**（由管理员维护、数量有限且稳定，用于前台导航与面包屑）；**标签是开放集合**（随写作自然增长，不预定义、不做层级）。这条约定决定两个管理页面的权限差异——分类的增改属管理行为，标签允许随文创建。

### 10.2 编辑填写的内容字段

| 字段 | 必填 | 形态 | 说明 |
|---|:---:|---|---|
| 标题 `title` | 是 | 单行文本 | 不允许全空白；上限 [建议] 200 字符 |
| 正文 `content` | 是 | Markdown 源文本 | 存 Markdown 原文，**不存渲染后的 HTML**，渲染由前台负责；可含 CMS 正文图片引用与视频链接（只存 URL） |
| 摘要 `excerpt` | 否 | 多行文本 | 选填，作者不写即为空；**CMS 不做自动截取**（前台如何兜底属前台展示逻辑，不在本系统范围） |
| 封面图 `cover` | 否 | 图片文件 | 可选；通过系统上传，遵循媒体资源规则 |
| 文章音频 `audio` | 否 | 音频文件 | 可选，**每篇最多一个**；通过系统上传，与封面图同构（见 6.5 与 BR-MEDIA-005） |
| 分类 `category_id` | 是 | 单选外键 | 一篇文章必须属于一个分类 |
| 标签 `tags` | 否 | 多选（N:M） | [建议] 每篇上限 10 个 |
| 预定发布时间 `scheduled_publish_time` | 否 | 日期时间 | 见 6.3；可为空即审核通过后立即发布 |

### 10.3 系统维护、编辑不可写的字段

| 字段 | 说明 |
|---|---|
| 状态 `status` | 6 值枚举，见 5.1；只能由状态机的迁移路径改变，不能直接赋值 |
| 归属编辑 `author_id` | 创建时写入，**此后不可修改**（BR-ISO-001） |
| 实际发布时间 `published_at` | 仅由系统在真正发布时写入（BR-PUB-006） |
| 创建时间 `created_at` | 系统写入 |
| 最后修改时间 `updated_at` | 系统写入 |
| 提交审核时间 `submitted_at` | [建议] 用于审核队列排序（先提交先审） |

### 10.4 不放在 `article` 表上的内容

驳回意见、下架原因、审核通过等**全部落在留痕表**（见 §7），不在 `article` 上放 `last_reject_reason` 之类的冗余字段——留痕是唯一事实来源。

由此带来一条查询要求：**文章列表需要显示"最近一次驳回/下架的原因与时间"**（这是 SRS §5.1「驳回」里"状态可见性"这条理由的具体落点，SRS §7.2 的（3）已把它立为查询要求）。它意味着列表查询要取每篇文章在留痕表里的**最新一条指定类型记录**，属于"分组取最新"的查询形态，实现时需注意别退化成 N+1 —— 这点留给 `architecture.md`。
