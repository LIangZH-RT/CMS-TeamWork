## Architecture Decisions

### 核心技术决策（均记录被否决的档与理由）

**缓存：完全不引入**（无 Redis / Spring Cache / Caffeine）。
理由不是省事——BR-MEDIA-003 要求下架后媒体**立即**停止匿名访问，任何缓存都会把"立即"悄悄变成"最多 N 秒后"；而这是整份基线里唯一落在**静态资源**而非数据行上的越权面，界面上完全看不出来。已立成有约束力的规定而非"暂不做"：**引入任何缓存之前，必须先显式定义全部失效点（下架、撤回、改期、编辑、删除、审核通过各一处），并把"状态变更必须同步失效缓存"立为一条新不变量。**
否决：Redis 只做会话；公开接口做缓存（BR-SEARCH-003 的"分页总数基于过滤后结果集"会被缓存计数重新打开侧信道）。

**归属隔离：MyBatis-Plus 行级拦截器自动追加 + scope 只有一个设置点**（`ArticleScopeBinder`）。
理由：BR-ISO-003 要求隔离在数据层强制执行、漏一处即漏洞，而读路径有 7 条（列表、筛选、计数、留痕、审核队列、媒体判权、公开接口）——手写条件意味着 7 个地方各可能漏一次，且漏写不报错、代码评审也看不出来。拦截器**只管 SELECT**，写路径收口到 `ArticleRepository` 的少数固定方法，这样"管理员不能改内容"（BR-007）成为结构性事实，而不是一个 scope 配置问题。
否决：每处手写归属条件；`ArticleScope` 作必填参数编译期强制（结构性最强，但所有 Mapper/Service 签名变形，留作升级方向）。

**媒体交付：全部经 Spring 控制器判权后由应用读盘返回**（`/api/media/{mediaId}` 是唯一出口）。
理由：磁盘 `storage/` 不对任何静态资源映射开放，也没有 Nginx 可直达的路径；判权与文章状态实时关联，SRS §9.1 第 3 条的"未公开内容不泄露"才成为可被用例证明的陈述。
否决：Nginx 直托管 + UUID 不可猜路径（"猜不到"不是"不可访问"，与 BR-MEDIA-003 正面冲突）；Nginx `X-Accel-Redirect`（生产标准解，但为性能引入环境复杂度）。
代价：文件 IO 经过 JVM，音频 20MB 会占用请求线程。

**认证与授权分界：Spring Security 只管认证，三道闸门自研在单一 `AuthzInterceptor`**。
理由：状态闸不适合写成注解表达式，判定一旦散到注解、Service 与框架配置三处，"权限判断只有一处"这个可证明性根基就没了。本项目对外演示的核心恰恰是这套权限模型。
否决：全量 Spring Security；全自研 Filter + 手写 CSRF（三样安全细节要自己写对，写错不报错）。

**拒绝响应一律 404，且响应体与"资源不存在"逐字节一致。**
理由：若角色闸返 403、归属闸返 404，攻击者仅凭状态码就能分辨"这篇文章存在但不是你的"，等于泄露存在性。**401 只保留给"根本没登录"**——它不携带任何目标资源信息，攻击者从自己的登录态本来就知道自己没登录。

**正文只存 Markdown 原文，绝不存渲染后的 HTML**；后端对正文字段不解析、不渲染、不做消毒——**一旦开始消毒，就等于承认这里可以进 HTML**。视频只存 `https` URL，只做协议校验，不判断链接目标内容。

**调度：`@Scheduled` + 单实例，幂等靠 SQL 不靠调度器。**
每篇文章的发布是一条带完整条件的 UPDATE：`status='待发布' AND scheduled_publish_time<=now AND published_at IS NULL`。即使意外起了第二个进程也不会重复发布或覆盖 `published_at`。整批使用**同一个** `now` 值（应用传入），不用 SQL `NOW()`。
否决 Quartz 与任何"发布任务表"——那会引入第二处任务状态来源，"任务已完成但文章未发布"这类不一致没有业务含义，只会制造排查成本。

**部分不变量不靠代码自觉，而是降级为结构约束**（本项目最有分量的一组决策）：
- `audit_log` 只增不改不删 → 降级为 **MySQL 表级权限**，应用账号只有 `INSERT`/`SELECT`。只靠"我们没写删除接口"的话，下次有人为了排查问题手写一条 SQL、或加个批量维护接口，约束就没了。
- 仅"无留痕的草稿"可删 → 降级为 **`audit_log.article_id` 外键 `ON DELETE RESTRICT`**，数据库层直接挡住，应用层不必再查一次。
- `audit_log` 操作人双主体 → 降级为 **CHECK `(actor_type='USER') = (actor_id IS NOT NULL)`**。外键 `RESTRICT` 的连带结论：只要一个账号还留着任何一条留痕就删不掉 ⇒ 将来实现「账号停用」只有停用一条路，删账号在结构上不可行。这不是新加的规则，是外键自带的。
- 越权测试跑 **Testcontainers 真 MySQL**，不用 H2——表级权限、`ON DELETE RESTRICT`、窗口函数这三样 H2 都不完整实现，在 H2 上跑通证明不了任何事。

**其它已定**：`user.role` 用单列枚举而非角色关联表（多对多会在数据层允许一个账号挂两个角色，与 BR-ROLE-001 直接冲突）；`author_id` 放组合索引首位（归属过滤是每个文章查询的必备条件）；后端按**功能域**分包而非三层（按层分包会让每次改动横跨四个目录）；`security` 不得反向依赖业务包；前端 `views/article` 与 `views/review` **不共享可写组件**（审核页根本没有正文编辑控件，这是 BR-007 的界面层结构性落实，不是目录洁癖）；"每篇取最近一条驳回/下架原因"用 MySQL 8 窗口函数 `ROW_NUMBER() OVER (PARTITION BY article_id ...)`，2 次查询不是 N+1，且子查询的 `article_id IN (...)` 必须用**已过滤、已分页**的当页 id（顺序反了会通过"返回了不属于我的文章的原因"泄露他人内容）。

### 规则层的承重墙（改这些要重新论证）

- **已发布的唯一入口是审核通过**（BR-010）。编辑不能自行发布、管理员不能手动发布、下架不能直连恢复——三条路全堵死，只剩审核。这是权限模型可证明性的根基：只要它成立，"任何未过审内容都不会对外展示"就能被穷举验证。
- **驳回是独立状态**，不是草稿的同义词。理由是状态可见性：编辑必须能从列表一眼分辨"还没写完"与"被打回"，否则会反复提交同一篇稿。
- **编辑之间隔离到文章**，全状态一视同仁，在数据层强制执行（BR-ISO-001~004）。这是整套需求里唯一有技术分量的部分——同角色越权（两个编辑）无法靠隐藏按钮蒙混。
- **已下架不是终态但必须重新过审**；下架原因与驳回意见同为必填（否则编辑面对"已下架"无从下手改什么，这个状态会变成事实上的死状态）。
- **待发布是可纠错窗口，不是锁定态**：可改期（内容未变，原审核结论继续有效）、可撤回（回草稿、结论作废、需重审）。改期的新时间必须晚于当前时间。
- **角色互斥**，一个账号只有一个角色 ⇒ `author ≠ reviewer` 是模型自带的结论，不需要写"禁止自审"的运行时校验——而那类校验漏一处就是漏洞。
- **只做结构化筛选，不做正文检索**；多标签筛选取**交集（AND）**。注意不能写成 `tag_id IN (1,2)`——那是并集语义，会多返回只命中一个标签的文章；须用分组计数或按标签逐个连接，且这套计数要与"过滤后分页"一起处理，否则分页总数会重新变成侧信道。
- **分类是封闭集合（单选，管理员维护）/ 标签是开放集合（多选，编辑可随文创建、扁平无层级）**。这条划分直接决定两个管理页面的权限差异。
- **仅"草稿且无任何留痕"可硬删除**，物理删不留标记。其余五种状态、以及"提交过又被撤回"的草稿一律不可删——因为撤回产生的草稿**是有留痕的**。
- **留痕共 7 类，只增不改不删**，操作人为 `USER`/`SYSTEM` 双主体。

**两条固定的过程检查项（本项目的教训）**：
1. **凡规则指向一份清单，先问这份清单从哪里派生。** 若答案是"人手抄的"，它迟早会漏，而且漏了不报错。本日两处缺口形状完全相同：规则指着一份从未存在或早已漏项的清单（图片白名单、留痕类别），而清单在两份文档里各抄一份、彼此吻合，看上去反而更自洽——**副本之间的一致性，证明不了任何一个副本的完整性。**
2. **把规则落成具体取值或表结构时做一致性检查**，光看文字看不出来。白名单缺口是"给字段填取值"时被逼出来的；BR-DEL 与 BR-PUB 的冲突是"把外键设为 `ON DELETE RESTRICT`"时暴露的。另有一例：写 v2 基线时把来源对话已确认的"创建、编辑、删除和发布"改写成"创建、编辑、保存、审核到发布"，**丢了一条已确认能力**，复核归档原文时才发现——改动措辞时会掉东西。
